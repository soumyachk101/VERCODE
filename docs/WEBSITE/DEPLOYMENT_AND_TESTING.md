# VERCODE Website — Deployment & Testing Plan

The deploy model + the test plan for the new `apps/website` deployable (`TECHNICAL_ARCHITECTURE.md §1` "a new `website` unit, sibling to `web`/`api`/`worker`"). It extends `OPERATIONS/DEPLOYMENT.md` (a 4th deployable row + a "verify" rule applied to the static bundle), `OPERATIONS/CI_CD.md` (a `check-website` target + a weekly scheduled-lane crawl job), and `docs/TESTING/E2E_TEST_PLAN.md` (a `website` E2E lane + a `J-website` journey). Every claim here is a *measurement* (a Lighthouse number, a `crawl-coverage` diff, a `sitemap.xml` fetch, a `ld-lint` count) — not a green checkmark (`RELEASE_CRITERIA.md §2` "the pass is a measurement, not a checkbox").

> **Implementation state (2026-10-23):** the 4 build-time sub-gates are wired into `make check-website` (the `@vercode/website` build + typecheck + the UT-web-* vitest suite + the anti-slop lint); the 3 host-side lanes (Lighthouse, axe, JSON-LD lint) are defined but not yet run.

## 1. The deploy model

### 1.1 The deployables table (a `DEPLOYMENT.md §1` extension)

`DEPLOYMENT.md §1`'s "The deployables" table gets a `website` row; the `api` row gains its two new website routes:

| Unit | What it is | New? | Stateful? | Scales on |
| --- | --- | --- | --- | --- |
| **`web`** | Next.js standalone build (`output: standalone`) | no | no | CPU / RPS |
| **`api`** | Fastify (auth, dashboard REST, webhook ingress, billing webhooks + **the two new website routes: `GET /api/answer` + `POST /api/track`**) | the routes are new; the unit is not | no | CPU / RPS |
| **`worker`** | the BullMQ consumer + the review pipeline | no | no | queue depth |
| **`website`** | a Next.js 15 **static export** (`output: export`) served from a **CDN static bucket** — a no state, no container runtime, no K8s/ECS autoscale | **yes** | **no** | **RPS via the CDN edge** |
| PostgreSQL 16 / Redis 7 | managed state for the *app*; the website bundle reads none of it at runtime (`TECHNICAL_ARCHITECTURE.md §4.3` "the website does not read the app's Postgres in P2") | no | yes | the existing scale path |

**The routing consequence:** `/api/answer` + `/api/track` deploy **with the existing `api` unit** (a new route in the existing lane, `TECHNICAL_ARCHITECTURE.md §5` "a new route in the existing lane" + "a new route" for the beacon) — they are part of the app's `worker`→`api`→`web` release, never part of the website's own deploy. The static bundle deploys **independently** (a `TECHNICAL_ARCHITECTURE.md §1` "the 3 independently-deployable units become 4").

### 1.2 Dev vs. prod

| | Dev | Prod |
| --- | --- | --- |
| Static host | a **Cloudflare Pages bucket** (a preview URL per PR, `TECHNICAL_ARCHITECTURE.md §3` "a Cloudflare Pages bucket (dev)") | a **CDN static host** (`TECHNICAL_ARCHITECTURE.md §3` "a Vercel (prod) or a Cloudflare Pages bucket (dev); both with **CDN + a zero-JS** default"; the exact vendor is the open `U5` decision, `PRD.md §8`) |
| `VERCODE_WEBSITE_BASE_URL` | `*.vercode.dev` (the dev placeholder, `PRD.md §8 U5`) | `vercode.com` (the launch prereq, `SAAS_LAUNCH_PLAN §3`) |
| The two API routes | the Compose `api` (`DEPLOYMENT.md §2`) with the mock providers | the app's prod `api` unit |
| Secrets | dev/mock values (`DEPLOYMENT.md §2` "the Compose dev-stack runs these as 'true'") | the platform secret store, KMS-wrapped (the `VERCODE_BEACON_SECRET`, `DEPLOYMENT.md §3` "no secret in an image layer") |

### 1.3 Rollout order (the website is NOT in the app sequence)

- **The app release** keeps its `DEPLOYMENT.md §4` sequence: migrate → `worker` → `api` → `web` (a rolling, readiness-gated deploy). The two new API routes (`/api/answer`, `/api/track`) land inside the *next* app release that carries them, with the `api` step.
- **The website deploy** is **independent**: a static bundle to the CDN bucket. It can land **before or after** the app release, and a website deploy *never* enters the `worker`→`api`→`web` sequence. Safety is one-directional (`TECHNICAL_ARCHITECTURE.md §1` "a website deploy doesn't touch the dashboard"):
  - *Website ahead of the API release*: safe — the P2 site has **no client-side data fetching** (`TECHNICAL_ARCHITECTURE.md §4.2` "no client-side data fetching in P2"; the on-page JSON-LD is build-time, `§4.1`). A `/api/answer` URL the API hasn't shipped is not *fetched* by any P2 page (the runtime fetch is the P3 "ask VERCODE" widget).
  - *API release ahead of the website*: safe — the routes are additive (`/api/answer` is a new route, not a contract change to existing routes, `TECHNICAL_ARCHITECTURE.md §1`), and the OpenAPI contract check (`RELEASE_CRITERIA.md` gate 11, the docs-drift gate extended to `OPENAPI.yaml`) still applies.
  - The **single shared source** is the build-time one: `content/pricing/` feeds both the site's JSON-LD and `/api/answer`'s fact table in one build (`TECHNICAL_ARCHITECTURE.md §4.1` "a pricing change in *one* file updates *everywhere*"), so a *content* PR that changes pricing re-generates both in the same build, even though the two *deploys* are independent.
- **The `content/` pipeline** (blog/docs/changelog) deploys **with the website bundle** (a content PR = a site rebuild, `TECHNICAL_ARCHITECTURE.md §2` "a website has no write path in P2 (a blog post is authored in the repo, CI-built, deployed)") — no CMS, no separate service.

### 1.4 Post-deploy verify (the "a verified deploy" rule)

`DEPLOYMENT.md §4` step 6: **"A verified deploy is one whose post-deploy checks passed — a deploy that 'shipped' but wasn't verified is marked *unverified*"** (restated in `DEPLOYMENT.md §7` "the 'verify' is a deploy, not a claim"). For a website deploy, the post-deploy checks are:

| # | Check | The pass means |
| --- | --- | --- |
| 1 | **the sitemap fetch** | `GET /sitemap.xml` → 200 + every `WFR-101` URL present (the `PERFORMANCE_AND_ACCESSIBILITY.md §2.2` sitemap-reachable check, run post-deploy against the live URL) |
| 2 | **the Lighthouse run** | the `PERFORMANCE_AND_ACCESSIBILITY.md §2.1` "Website Lighthouse" lane re-run against the *deployed* URL (mobile ≥ 90 on the 5 budget pages, `WNFR-01`/`WNFR-02`) — the post-deploy number is recorded, not the CI number |
| 3 | **the JSON-LD validity** | the `ld-lint` run on a sample of the deployed pages (`TECHNICAL_ARCHITECTURE.md §5` "Website JSON-LD validity… 0 errors") |
| 4 | **the `/api/answer` smoke** | `GET /api/answer?q=<a bounded query>` on the *API* host → 200 + a `ProductFact` JSON body matching `content/pricing/` (the "single source of truth" check, `TECHNICAL_ARCHITECTURE.md §4.2` — a *fact lookup*, and the smoke proves the lookup still points at the right source after the deploy) |

A website deploy record is a release report: the bundle tag, the 4 check results, and **status: verified / unverified** (`DEPLOYMENT.md §7` "a deploy record (the release report) states: the image tags, the migration version, the canary bake results, the health checks, the post-deploy verification… and the **status: verified / unverified**"). An unverified website deploy is *flagged* (not claimed live) until re-verified or rolled back — the `DEPLOYMENT.md §5` "marked 'live integration blocked', not 'deployed'" posture applied to a static surface.

### 1.5 Rollback

The previous static bundle is retained; a rollback is a **re-deploy of the previous `out/` + a CDN cache-purge** (the `DEPLOYMENT.md §6` "the previous image is retained; a rollback is a re-deploy of the previous image" rule, applied to a static artifact). There is no migration step (no DDL, `TECHNICAL_ARCHITECTURE.md §4.3` — the website has no DB coupling). A pricing rollback is a `content/pricing/` revert + re-build + re-deploy (the single-source rule means the `/api/answer` revert is a separate *API* release if the route's fact table was rebuilt).

## 2. The `.env.example` additions

The three new vars are `TECHNICAL_ARCHITECTURE.md §6`'s ("the `.env.example` gets 3 new placeholder rows (the docs-drift check)"). They follow the `.env.example`'s header convention (a grouped projection of `ENVIRONMENT_VARIABLES.md`, a one-line comment per var, placeholders only — `NFR-31`, `SECRETS_MANAGEMENT.md §4` "no real secret in this file"):

| Var | Required? | Where it's used | Note |
| --- | --- | --- | --- |
| `VERCODE_WEBSITE_BASE_URL` | yes (prod) | build-time: `sitemap.xml` + `robots.txt` + `<link rel="canonical">` + `og:url` (`TECHNICAL_ARCHITECTURE.md §6`; the domain is the open `U5`, `PRD.md §8`) | a build-time var (a static export bakes it in; the prod value is the placeholder `https://vercode.com` in `.env.example`, `*.vercode.dev` in dev) |
| `VERCODE_WEBSITE_OG_DEFAULT` | no | build-time: the default OG image path (`WFR-404` "a VERCODE-default OG image (1200×630)"); a per-blog image is the front-matter field (`WFR-303`) | a build-time var; the empty placeholder means "use the asset-manifest default" |
| `VERCODE_BEACON_SECRET` | yes (prod) | runtime: the HMAC key for `POST /api/track` on the *api* unit (`TECHNICAL_ARCHITECTURE.md §6` "a `SECURITY/SECRETS_MANAGEMENT.md`'s 'a secret in the .env.example placeholder' rule — no secret in an image, `DEPLOYMENT.md §4`") | a placeholder `<KMS-wrapped HMAC key>` only; the real value lives in the secret store, KMS-wrapped |

**The env-drift-check gate** (a `scripts/env-drift-check.mjs` + the Makefile `env` target, `ENVIRONMENT_VARIABLES.md §10` "the `.env.example` is a the generated artifact + a the checked in (a the no secret, a the doc-drift check)"): the script's rule is that the `.env.example` var set must match the `config` package's `KNOWN_VARS` (the source of truth, `packages/config/src/index.ts`) plus the whitelisted `KMS_VARS` + `DOC_ONLY_VARS` sets (the script's own comment: "a the KMS vars… are *not in* a the KNOWN_VARS… so a the check whitelists a the KMS vars as a the 'a the doc's vars that aren't a the config package's vars'" + "a the DOC_ONLY_VARS (a the config package's no-read vars… the .env.example's projection includes them)"). So the three new vars must be added, in one PR:

1. a new **`ENVIRONMENT_VARIABLES.md` section** (a `§11. Website`, the `TECHNICAL_ARCHITECTURE.md §6` "the table, new rows" — the "a variable not in this doc doesn't exist" rule, `ENVIRONMENT_VARIABLES.md §9`);
2. a `.env.example` **group** (`# --- §11 Website ---`, a one-line comment per var, a placeholder value — the "no real secret" rule);
3. the **`KNOWN_VARS` / `KMS_VARS` / `DOC_ONLY_VARS`** sets in the `env-drift-check.mjs`'s classification: `VERCODE_BEACON_SECRET` is a *KMS-class* secret (a placeholder in `.env.example`, the real value in the secret store) — the check whitelists it as "the doc's vars that aren't the config package's vars"; `VERCODE_WEBSITE_BASE_URL` + `VERCODE_WEBSITE_OG_DEFAULT` are *build-time* vars the runtime `config` package doesn't read (a `DOC_ONLY` class, the `AI_FOBID_TRAINING` precedent in the script). A 3-way drift (a var in one of the three places but not the other two) is a **CI failure** (the `make env` target, `ENVIRONMENT_VARIABLES.md §10` "a drift between the doc and the example is a CI failure, the `RELEASE_CRITERIA` gate 11 family").

**The gate:** `make env` (the `Makefile`'s `env` target — "the .env.example's doc-drift check") runs in the *merge* lane as part of the docs-drift family (`RELEASE_CRITERIA.md` gate 11, the docs-drift gate; `CI_CD.md §1` "a docs-drift check" in the PR lane). This is an **extension** of the existing docs-drift gate, not a new gate number.

### 3.3 The lane's trigger (a `CI_CD.md §1` lane-convention placement)

- **a PR touching `apps/website/**` or `content/**`**: the `Website build` + a `JSON-LD validity` + a `sitemap`/`robots` static check (a fast, no-browser sub-set, the `CI_CD.md §1` "the PR lane… *no external creds*" rule).
- **a merge to `main`**: the **full `gate 14` lane** (a Lighthouse + a axe + a link-checker + a `gate 14`'s 2 route checks), as a **separate merge gate** (a `TECHNICAL_ARCHITECTURE.md §5` "the website lanes are independent CI runs" — a red `gate 14` holds the *website* deploy, not the *app* deploy; the two are decoupled gates, `DEPLOYMENT.md §1`'s independence rule extended).

## 5. Security notes for the public surface

### 5.1 No cookies (the `WFR-504` + `INFORMATION_ARCHITECTURE_AND_PAGES.md §6` "no cookie banner in P2")

The site **sets no cookies** (a `INFORMATION_ARCHITECTURE_AND_PAGES.md §6` "the site sets no cookies — the cookieless beacon, `WFR-504`"; a cookie banner would be *dishonest* — there's nothing to disclose). The *only* outbound telemetry is the **first-party cookieless beacon**: a `POST /api/track` on the *API domain* (a `TECHNICAL_ARCHITECTURE.md §4.2` "a `?src=web-{page}` beacon → a first-party cookieless `POST /api/track` (a new route on the `apps/api`)… a 204 response, no cookie, no PII"), fired on the `/signin` activation (`WFR-504` "a one first-party, cookieless beacon on a `/signin` success"), **HMAC-keyed** with a `VERCODE_BEACON_SECRET` (a `TECHNICAL_ARCHITECTURE.md §6` "a HMAC key for the `POST /api/track` (a `SECURITY/SECRETS_MANAGEMENT.md`'s 'a secret in the .env.example placeholder' rule)"), the `?src=web-{page}` param only (a `WFR-504` "the beacon URL carries a `?src=web-{page}` param; no third-party analytics in P2 (the DPDP posture, `SECURITY/PRIVACY.md`)"). **A `Set-Cookie` on the beacon response is a `gate 5` / a `gate 14` fail** (a `TECHNICAL_ARCHITECTURE.md §5` "the beacon `/api/track`: a cookieless-ness check (a `Set-Cookie` is absent; a 204 response; a PII redaction check)").

### 5.2 The CSP for the static export (a recommended policy block)

A `Content-Security-Policy` on the static export (a `next.config.ts` `headers` + a CDN edge, a `TECHNICAL_ARCHITECTURE.md §3` "a `Next.js 15… output: export`"). The policy's *recommended* block:

```
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'unsafe-inline';   /* the inline JSON-LD <script> blocks are data-only (no executable JS);
                                         the *executable* JS is all self-hosted + hashed (the _next/static/ assets) */
  style-src 'self';
  img-src 'self' data:;                /* the static OG + the hand-authored screenshots (WNFR-05); no external image */
  font-src 'self';                     /* the @fontsource self-hosted bundle (WNFR-05); a Google-Fonts request is a WNFR-04 violation */
  connect-src 'self' https://api.<vercode-domain>;   /* the cookieless beacon POST /api/track only (a WFR-504); no third-party */
  base-uri 'self';                     /* no open-redirect via a base tag */
  form-action 'self';                  /* no external form (the "no newsletter form in P2" rule, DESIGN_SYSTEM_AND_TYPOGRAPHY.md §3) */
  frame-ancestors 'none';              /* no clickjacking (the site is never an iframe) */
  upgrade-insecure-requests;           /* the DPDP posture: no mixed-content, a SECURITY/PRIVACY.md */
```

**The `script-src 'unsafe-inline'` caveat (stated, not hand-waved):** a fully static export *cannot* use a per-request CSP nonce (a nonce is a *server-rendered* per-response value; a static `out/` is a *build* artifact, not a per-request render). So the inline *JSON-LD* `<script type="application/ld+json">` blocks (a `TECHNICAL_ARCHITECTURE.md §4.1` "a per-page JSON-LD `<script>`") need an `'unsafe-inline'` carve-out. That carve-out *also* permits inline `onclick`/`onerror` handlers — a *static* site with no user-input surface (a `INFORMATION_ARCHITECTURE_AND_PAGES.md §6` "a no user accounts on the marketing surface") has a *low* blast radius, but it is a **weaker** policy than a nonce + a hash. **A P3 hardening** (a `UNRESOLVED` §6): **move the JSON-LD from an inline `<script>` to a `<meta itemprop>` microdata** (a *no-CSP-carve-out* option, the `ld-lint` check is a `<meta>`-tag version, a `TECHNICAL_ARCHITECTURE.md §5` "a `ld-lint` (or a `schema-dts` type check)" — the `ld-lint` is the tool that *validates* whichever form is chosen, so a P3 microdata switch is a `gate 14` re-run, not a new gate). **A P2 position:** the `'unsafe-inline'` carve-out is *accepted* (a `TECHNICAL_ARCHITECTURE.md §5` "a `ld-lint` (or a `schema-dts` type check)" + a `DESIGN_SYSTEM_AND_TYPOGRAPHY.md §3` "a `no external font request`" rule + a `WNFR-04` "a no third-party requests") — a *weaker* but *documented* + a *P3-hardened* CSP, not a *silent* one.
