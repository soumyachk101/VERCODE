# VERCODE — Known Limitations

The *honest* list of what the MVP does *not* do, and why — a "don't claim what you can't verify" applied to *capability* (a feature that's *deferred* or *not-present* is *documented*, not *silently absent*). This doc is the *counterpart* to `MVP_SCOPE.md` (the "in MVP" list) — together they define the *exact* scope of what's built + what's *known-missing*.

## 5. The *what's *not* a known limitation* (a the *counter-list*, a "don't *over*-claim")

To *prevent* the "we claim a feature that's not there" failure mode, the things that are *NOT* limitations (a they *are* in scope + a they're *measured*):
- **The *deterministic* static analysis is *in* MVP** (a `ADR-005` the "deterministic-first pipeline"; a `UT-static-sql-01` the "a provider-down still publishes the static finding") — a *a "no static analysis" is NOT a limitation, a the static analysis is a MVP feature*.
- **The *tenant isolation* is *in* MVP** (a `NFR-07`, a `IT-tenant-01..05` the "re-run on every schema change") — a *a "cross-tenant leakage" is NOT a known limitation, a it's a release-gate property*.
- **The *prompt-injection defense* is *in* MVP** (a `NFR-09`, a `ST-injection-01..04` the "a regression blocks the release") — a *a "the AI can be prompt-injected" is NOT an accepted limitation, a it's a designed defense + a release gate*.
- **The *cost tracking* is *in* MVP** (a `FR-310`, a `AC-306` the "a every completed job records the input/output tokens + the est_usd_cost") — a *a "no cost tracking" is NOT a limitation, a it's a MVP feature*.

**The *counter-list* exists to keep the "known limitations" honest:** a limitation is a *documented absence* (a `L-*` the "not in MVP, lands in Phase X"), a *not* a *documented presence-that-we-forget* (a the "static analysis is in MVP" is NOT a limitation). A limitation list that *omits* a present feature as a "limitation" is a *doc error*; a limitation list that *includes* an absent feature as a "present" is a *false claim* (a `PHASE 9 "do not fabricate… features"`).

## 6. The *cross-reference* to the *`MVP_SCOPE.md`* + the *`RELEASE_CRITERIA`*

- **`MVP_SCOPE.md`** is the "in MVP" list (a the P0 complete + the explicit P1 must-haves); **this doc** is the "NOT in MVP" list (a the P1/P2/P3 deferrals + the *honest* limits). Together: a *a feature is either in `MVP_SCOPE` or in this doc's `L-*`/`Q-*`/`C-*`/`O-*` list, a never in both, a never in neither* (a the "complete + disjoint" scope invariant).
- **A *`RELEASE_CRITERIA` gate*** is a *verification* that a limitation is *still a limitation* (a `L-1` the "no execution" → a `ST-malicious-file` the "a manifest is analyzed, not executed"; a `L-8` the "live-blocked" → a `CI_CD.md §7 "a blocked lane is reported as blocked"`). A limitation that's *no longer* a limitation (a Phase 2 lands the sandbox) is *removed* from this doc + a *the gate* changes (a `ST-sandbox-*` becomes a release gate, a `SANDBOX_SECURITY.md §8`).
