<p>Install the GitHub App on one repository and open a pull request; the review lands as a summary comment plus validated inline findings. This is the public mirror of the J1 onboarding journey: sign up, install, open a PR, read the review. No configuration is required between the install and the first published review.</p>
<p>The activation bar is a measured one: an org that installs the App and publishes its first review within 10 minutes of the install counts as activated. That is the KPI the funnel is built against (the SUCCESS_METRICS activation target), and the rest of this page is how to hit it.</p>
<h2 id="before-you-start">Before you start</h2>
<p>The two prerequisites, and nothing else:</p>
<ul>
  <li>A GitHub account with admin rights on at least one repository. The App is installed at the organization or repository level; you need the permission that grants the install.</li>
  <li>A VERCODE account. Sign up on the dashboard; you become the owner of a new org on first sign-in.</li>
</ul>
<p>That is the whole of the setup. No provider key is required for a first review on the Free plan: the platform's default provider is used until a BYOK key is set.</p>
<h2 id="install-the-app">Install the App</h2>
<ol>
  <li>From the dashboard, open the repositories page and choose <strong>Install VERCODE</strong>. The install URL is generated server-side and is pre-scoped to the least-privilege permission set: <code class="mono">contents:read</code>, <code class="mono">pull_requests:write</code>, <code class="mono">checks:write</code>, <code class="mono">metadata:read</code>, <code class="mono">issues:read</code>. No <code class="mono">admin:org</code>, no secrets scope. The full scope table is on the GitHub App page.</li>
  <li>Authorize the install on GitHub and select at least one repository.</li>
  <li>GitHub dispatches the <code class="mono">installation</code> webhook; VERCODE records the install and discovers the connected repositories through <code class="mono">installation/repositories</code>. The repositories page now lists them with an active status.</li>
</ol>
<p>The install takes under a minute. The repository does not need to be public; the App's read scope covers private repositories on the same account.</p>
<h2 id="open-a-pull-request">Open a pull request</h2>
<p>Open a pull request on a connected repository — a new branch is fine, an empty merge is not. GitHub dispatches the <code class="mono">pull_request</code> webhook on open, reopen, or synchronize. The webhook is verified and a review job is enqueued; the pipeline runs and publishes the result.</p>
<ul>
  <li>The review publishes at p50 under 120 seconds and p95 under 300 seconds, from webhook receipt to GitHub publication (NFR-02, on a 50-file diff with 500 changed lines or fewer).</li>
  <li>The publication is a summary comment with the verdict and a severity count, plus inline findings anchored to the verified changed lines (FR-206). If a line anchor fails, the finding lands in the summary instead of a wrong line.</li>
</ul>
<h2 id="read-the-review">Read the review</h2>
<p>Open the pull request on GitHub and read the VERCODE comment. The summary states the verdict (approve, needs changes, or none of concern) and the top risks; each inline finding carries a category, a severity, a confidence, a reason, and a suggested fix.</p>
<p>The same review is on the dashboard, under the org's reviews list, with its cost, its status, and the per-finding detail. That dashboard view — not the PR comment — is the exit criterion: from &quot;connected GitHub&quot; to &quot;first review visible in the dashboard&quot;, without any configuration except the install and, on a paid plan, a provider key.</p>
