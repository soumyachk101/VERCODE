Questions, answered

Getting started
Does VERCODE post comments on my pull requests?
Yes. VERCODE posts a summary comment with the verdict and a severity count, plus inline comments anchored to the verified changed lines. If a line anchor fails validation, the finding is written into the summary comment instead of dropped. This is the FR-206 publication path.
How fast is a review?
A review publishes at p50 under 120 seconds and p95 under 300 seconds, measured from the webhook receipt to the GitHub publication, on a 50-file diff with 500 changed lines or fewer. That is the NFR-02 latency target. A diff past the file or line budget degrades to the highest-risk files rather than stalling.
Will it flood my PR with comments?
No. Findings under the confidence floor are not posted, and the floor defaults to 0.6 and is configurable per org and per repo (FR-308). You can also suppress an entire category for one repo. The deterministic static-analysis pass is exempt from the floor, because its precision is measured, not estimated.
What languages does it support?
VERCODE classifies each changed file by language and risk tier before the AI stage (FR-302). The classification is what routes the work: security-sensitive files, database-touching files, dependency manifests, generated code, and test files each get a distinct review treatment. A diff is reviewed file by file, not repo by repo.
Reviews & findings
Does it run my tests?
No. The pipeline analyzes the diff with static analysis and a model pass; it does not execute the PR's install or test steps. Running untrusted code in the product is a known-severity threat class, so it is closed by absence in the MVP (L-1). Sandboxed test execution is the Phase 2 item on the roadmap, and the known-limitations doc says so in plain terms.
Which AI models does it use?
Model calls are task-routed, not a single model for everything (FR-311). Routine triage and summary go to a cheaper model; the deep review and the security pass go to a stronger one. OpenAI is the first provider; Anthropic and a self-hosted Ollama adapter follow as Phase 1. The routing table lives in config, so a model swap is a config change, not a code change.
Can I bring my own API key?
Yes. An org admin sets a provider key at the org level, and VERCODE encrypts it with AES-256-GCM under a KMS-wrapped master key (FR-313). While the key is set, the model calls run on your key and your spend. The key is masked in the dashboard, and revoking it is immediate: the wrapped row is hard-deleted.
Where is my code stored?
Your source is not stored as a durable asset. Raw diffs and file contents live in an org-scoped cache with a 24-hour TTL and in worker memory for the review's duration (NFR-28). What persists is the analysis: findings and summaries, retained for your plan's window, then hard-purged on schedule. A finding may quote a bounded snippet of the diff; the full file does not reach the database.
Security & privacy
Does it send my code to a third party?
The model calls go to the configured AI provider: the changed files plus one-hop imports, inside a token budget, never the whole repository, on the provider's no-training contract (NFR-29). With BYOK the call runs on your key; on Ollama it stays on your infrastructure. The deterministic static-analysis pass runs in your pipeline and never leaves it (NFR-09).
Which GitHub permissions does the App need?
The GitHub App requests five scopes, all read-only except the publication path: contents:read, pull_requests:write, checks:write, metadata:read, and issues:read (FR-210). No admin:org, no secrets scope. The pull_requests write is where the review is posted; everything else is a read.
Does it work on pull requests from forks?
Yes, on a restricted path. A PR from a fork arrives as a pull_request_target event; the review runs in a sandboxed context and publishes only on the base repository's PR, not on the fork (FR-203). Code from an untrusted fork is analyzed, never executed.
How do I silence a noisy category?
Create a custom rule that suppresses the category, scoped to the whole org or to a single repository (FR-505). The rule types are category suppression, a confidence-floor override, quiet categories, and per-language toggles. Rules are versioned: a change is audit-logged and applies from the next review, not the in-flight one.
Billing & limits
What happens when I hit my quota?
The review is skipped with a notice posted on the pull request, and a dashboard row and banner show the reason and the upgrade path (NFR-18: skip-with-notice, never a silent stop). The skip happens before the AI stage, so it consumes zero tokens. The 80% warning on the quota strip is the early signal that the cap is near.
Is VERCODE open source?
Yes. The repository is MIT-licensed, with the license at LICENSE.md. The review pipeline, the static-analysis rules, and the dashboard code are in the tree. The docs are written so that each claim can be checked against the code it points at; the open-source posture is a differentiator, not a garnish.
Can I self-host it?
The code is self-hostable: the repo is MIT-licensed. The hosted pipeline needs two external credentials: the GitHub App installation and an AI provider key. With BYOK or Ollama the model spend is on your bill, not VERCODE's — the Enterprise plan is built around exactly this cost-shifting shape.
How do I export or delete my data?
Removing the GitHub App installation triggers deletion: the install is marked removed, the diff cache is evicted immediately, and an export window opens for your findings before any hard-purge (FR-404). Findings are retained 30 days on Free, 90 on Developer, 365 on Team, or custom on Enterprise; the audit log keeps a 180-day minimum regardless of plan (NFR-27).
